# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a **single git monorepo** (one `.git`, at the root) containing three deployable
projects plus shared deploy infra. It was consolidated from three formerly separate repos
(`GeoBradDev/WebGIS-Django` / `-React` / `-React-Native`), whose histories were dropped.

- `backend/` — Django + Django Ninja + GeoDjango/PostGIS REST API. Package `webgis`.
- `frontend/` — React 19 + Vite web client (MapLibre GL JS + PMTiles). Package `webgis-react`.
- `mobile/` — Expo / React Native mobile client (TypeScript). Package `webgis-react-native`.
- Root: `docker-compose.yml`, `.do/app.yaml`, `README.md`, `ARCHITECTURE.md`, `.gitignore`.

The two clients are alternative frontends for the same backend; there is no shared build or
package linkage between the three (each has its own dependencies and tooling). App Platform
builds each component from its `source_dir` within the one repo. See `ARCHITECTURE.md` for the
full design. The goal is a forkable, boilerplate WebGIS **template**.

Note: CI runs only from root `.github/workflows/` (`backend-ci.yml`, `frontend-ci.yml`); the former
stray `backend/.github/`, `frontend/.github/`, and root `pyproject.toml` no longer exist. See
ARCHITECTURE.md §9 for current known issues.

## Commands

### Containerized stack (repo root) — the recommended path
- `cp backend/.env.example backend/.env && cp frontend/.env.example frontend/.env` (set `SECRET_KEY`), then `docker compose up --build` — runs `db` (postgis), `backend` (migrates on boot, `http://localhost:8000`), and `frontend` (Vite, `http://localhost:5173`).
- `docker compose --profile celery up` also starts `redis` + a Celery worker.
- `POSTGRES_HOST_PORT=5433 docker compose up` if host port 5432 is taken.
- `docker compose exec backend python manage.py createsuperuser`.

### backend/ (without containers: `source .venv/bin/activate`)
- Dev server (ASGI): `python manage.py runserver` (API at `/api`, admin at `/admin`, allauth headless at `/_allauth/`, health at `/healthz`).
- Migrations: `python manage.py makemigrations` then `python manage.py migrate`.
- Tests: `pytest` (via `pytest-django` + `pytest.ini`; needs a PostGIS database, from which Django builds an isolated test DB). `api/tests.py` covers feature CRUD, spatial queries (incl. geography distance/coveredby), geometry + query-param validation, the GDAL raster pixel read and path guard, the `import_demo_features` command, and the email-first user manager.
- Celery worker (only when `REDIS_URL` is set): `celery -A WebGIS worker -l info`.

### frontend/ (run from `frontend/`)
- Dev: `npm run dev` (Vite, `http://localhost:5173`). Build / preview: `npm run build` / `npm run preview`.
- Lint: `npm run lint` (ESLint flat config).
- Note: the project is plain JS/JSX with no Jest or TypeScript; the formerly non-functional `test`/`type-check`/`prettier` npm scripts were removed. Use `npm run lint` for static checks and `npm run build` to catch import/syntax errors.

### mobile/ (run from `mobile/`)
- Dev: `npm start` (Expo). Targets: `npm run android`, `npm run ios`, `npm run web`. Tests: `npm test` (`jest-expo`).
- Requires `GOOGLE_MAPS_API_KEY` in a `.env` (consumed by `app.config.js`).

### Local first-run helper
`backend/scripts/bootstrap.sh` provisions a host (non-container) PostgreSQL/PostGIS + venv + `.env` + migrations + superuser. Deploy config is no longer generated by it — it lives in committed `docker-compose.yml` and `.do/app.yaml`.

## Backend architecture

- **API layering (Django Ninja).** `backend/api/api.py` only builds the root `NinjaAPI` instance (`api`) and assembles per-domain routers from `api/routers/` (`features.py` = Point/Polygon/Line CRUD + queries; `spatial.py` = joins, nearest, geometry ops; `gdal.py`). Views stay thin and call `api/services.py` (ORM + GEOS/GDAL logic); request/response models live in `api/schemas.py`. `WebGIS/urls.py` mounts `api` at `api/` plus a DB-free `/healthz`. To add an endpoint: route in the relevant `routers/*.py` → logic in `services.py` → schemas in `schemas.py`. Routing: `/api/points|polygons|lines/...`, `/api/spatial/...`, `/api/gdal/...`.
- **Conventions:** In/Out/Patch schemas via `ModelSchema` + `resolve_*`; `get_object_or_404` for 404s; `(status, data)` tuples with declared `response={code: Schema}`; list endpoints are `@paginate`d (LimitOffset, `{items, count}`); geometries are exchanged as real **GeoJSON objects** (not strings); numeric/coordinate query params are bounded with `Query(...)` constraints; a bad geometry raises `services.InvalidGeometry` → 422 via an exception handler; GDAL file-path endpoints are confined to `settings.GDAL_FILE_ROOT` (`services._safe_path`).
- **Geospatial stack.** Models (`api/models.py`) use GeoDjango fields, all `srid=4326`. `DemoPoint.geom` is a PostGIS **geography** column (`api/0006`), so `geom__dwithin`/`Distance` run in metres on the spheroid and stay index-assisted; point-in-polygon uses `geom__coveredby` (geography has no `ST_Within`). `DemoPolygon`/`DemoLine` stay geometry (`geom__intersects`, etc.). Measurements avoid the degrees-vs-metres trap: **area** = `Area(Transform(geom, 6933))` (global equal-area), **buffer** reprojects to a local azimuthal-equidistant CRS; centroid, simplify (`ST_SimplifyPreserveTopology`), and union run server-side via GIS DB functions/aggregates. The GDAL endpoints call `osgeo` directly, forcing traditional `(lon, lat)` axis order (GDAL 3 uses authority order) and reading pixels via `ReadRaster` (no `gdal_array`/NumPy bridge). Demo models are registered with `GISModelAdmin` (admin map widget); `manage.py import_demo_features` is a `LayerMapping` example loading `api/sample_data/demo_polygons.geojson`. **Note:** the demo models carry only `name`, `description`, geometry, and `created_at` (`description`/`created_at` added in `api/0005`), so `GET /api/polygons` has no domain-rich attributes and is not a drop-in source for the attribute-rich web overlay (see web architecture).
- **PostGIS extension.** Migration `api/0004_enable_postgis` runs `CreateExtension('postgis')` with `run_before` set ahead of `api/0002` (the first geometry columns), so a fresh DB (e.g. DO Managed Postgres, where PostGIS is available but not enabled) migrates cleanly. The local `postgis/postgis` image already has it.
- **Custom user model.** `api.CustomUser` (via `AUTH_USER_MODEL`) authenticates by **email** (`USERNAME_FIELD = 'email'`), stored lowercased. The custom manager is **email-first**: `create_user`/`create_superuser` key on email (normalising it), and `get_by_natural_key` does case-insensitive lookup. `createsuperuser` and `bootstrap.sh` pass `email`/`username` as keyword args.
- **Auth is django-allauth headless.** `HEADLESS_ONLY = True`; clients hit `/_allauth/app/v1/auth/...` with an `X-Session-Token`. Email verification is mandatory; verification/reset links are built from `FRONTEND_URL` in `HEADLESS_FRONTEND_URLS`. No DRF, no custom token app. Django Ninja 1.6 has no `csrf` kwarg, so the token API needs no special handling (CSRF-exempt with no session auth); `CsrfViewMiddleware` is enabled to protect the cookie-auth admin.
- **Async email / Celery is optional.** `ACCOUNT_ADAPTER = api.adapters.AsyncAccountAdapter` dispatches allauth emails (preserving the rendered HTML alternative) via the `send_email_async` Celery task. Celery is enabled only when `REDIS_URL` is set; otherwise `CELERY_TASK_ALWAYS_EAGER` runs tasks inline.
- **Config is env-driven** (`WebGIS/settings.py` + `python-dotenv`; helpers `env_bool`/`env_list`). Prod prefers a single `DATABASE_URL` (via `dj-database-url`, engine forced back to PostGIS, with `conn_health_checks`), falling back to discrete `POSTGRES_*` locally. `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CORS_ALLOWED_ORIGINS`, `FRONTEND_URL` come from env. Security is `DEBUG`-gated: when `DEBUG=False`, CORS is restricted to `FRONTEND_URL`, the `SECURE_*`/proxy-SSL/HSTS settings turn on (App Platform terminates TLS via `X-Forwarded-Proto`), logging goes to stdout only, and a missing `SECRET_KEY` is a fail-fast error (insecure default only in dev). Email is env-driven and defaults to the **console backend in dev**; serving the allauth headless OpenAPI spec (`HEADLESS_SERVE_SPECIFICATION`) needs the `django-allauth[headless-spec]` extra. See `backend/.env.example` for the full var list.

## frontend/ architecture

- **Components live in `frontend/Components/` (capital C), a sibling of `src/`, not inside it.** `src/` holds the entry (`main.jsx`), shell (`App.jsx`), routes (`AppRoutes.jsx`), the Zustand stores, `mapStyle.js`, and `layers.js` (the layer registry). Imports cross this boundary (e.g. `App.jsx` imports `../Components/Sidebar.jsx`).
- **Map: MapLibre GL JS via `react-map-gl/maplibre`** (not Leaflet). `Components/Mapview.jsx` registers the `pmtiles://` protocol once at module scope, then renders `<Map>` with `<Source>/<Layer>` children. `src/mapStyle.js` builds the style from env: a **PMTiles vector basemap** (Protomaps schema via `protomaps-themes-base`) when `VITE_BASEMAP_PMTILES_URL` is set, otherwise raster OpenStreetMap so the map works out of the box. `BASEMAPS`/`DEFAULT_BASEMAP_ID` drive the in-map basemap switcher (`activeBasemap` in the store). **Axis order:** the store keeps Leaflet-style `[lat, lng]`; convert to maplibre `[lng, lat]` only at the map boundary inside `Mapview.jsx`.
- **Config-driven layer registry.** `src/layers.js` (`LAYER_CONFIGS`) is the single source of layer definitions: each entry has a `source` (`{kind:'geojson-url', url}` or `{kind:'backend', endpoint}`), a `style`, and (on the one `primary: true` layer) the field metadata — `columns`, `categoricalFilters`, `rangeFilter`, `dashboard`, `popup` — that drives the table, sidebar filters, dashboard, and map popups. Add/swap a layer by editing this file, not the components. Ships two examples: the St. Louis municipalities overlay (`geojson-url`, primary, from `VITE_MUNI_GEOJSON_URL`) and a `Demo Polygons (backend API)` layer (`kind:'backend'`, `GET /api/polygons`) — the reference pattern for consuming the template's own backend. PMTiles remains the basemap layer.
- **Two Zustand stores:**
  - `src/store/useStore.js` — map/UI state plus the layer registry: center, `currentView` (`map`/`dashboard`), table collapse, snackbar, `activeBasemap`, the `layers` map, generic fetching (`fetchLayers`, supporting both source kinds), and primary-layer filtering (`getFilteredPrimaryData`, `getUniqueValues`, `setCategoricalFilter`, `setRange`).
  - `src/store/useAuthStore.js` — auth, **persisted to `localStorage`** (key `auth-storage`). The allauth base is derived from `VITE_API_URL` (strip `/api`), not hardcoded.
- **Routing.** `react-router-dom` v7: `/`, `/verify-email/:key`, `/reset-password/key/:key` (the latter two match the backend's `HEADLESS_FRONTEND_URLS`).
- **UI stack.** Material UI v7 (`@mui/material`, `@mui/x-data-grid`), Recharts for the dashboard. Snackbar constants in `constants/snackbarMessages.js`.
- Vite `base: '/'` (root-served on App Platform). Env vars (`VITE_*`) are inlined at **build** time — see `frontend/.env.example`.

## mobile/ architecture

- **expo-router file-based routing.** Screens under `app/`; tabs under `app/(tabs)/`. The map screen (`app/(tabs)/index.tsx`) renders `components/MapViewWrapper.tsx`, which wraps `react-native-maps`.
- **Zustand stores** in `store/`: `useMapStore.ts` (region) and `useAppStore.ts` (loading flag + `sessionToken`).
- This client is **TypeScript** (`.ts`/`.tsx`), unlike the JS web client. The README's described structure (`screens/`, `App.tsx`) is stale; the real entry is `expo-router/entry`.
- **PMTiles is deferred on mobile** (would require `@maplibre/maplibre-react-native` + an Expo dev build). Mobile is not deployable to App Platform (ships via EAS / app stores).

## Deployment

- **Local containers:** `docker-compose.yml` (repo root) — `db` (`postgis/postgis:16-3.4`, healthcheck), `backend` (built image, migrates on boot via `entrypoint.sh` gated by `RUN_MIGRATIONS`), `frontend` (Vite dev server), optional `redis`/`celery` profile. `env_file` entries are `required: false` so the stack parses before `.env` files exist.
- **Backend image:** `backend/Dockerfile` is multi-stage on `python:3.14-slim-bookworm` (Django 6.0). GDAL is installed from the distro and the Python binding is pinned to `gdal-config --version` (the container ends up on GDAL 3.6.2); `requirements.txt` keeps its own `GDAL==3.4.1` pin for the maintainer's host install, which the Dockerfile strips. `collectstatic` runs at build (whitenoise manifest storage); runs as non-root `appuser`; serves via `gunicorn ... -k uvicorn.workers.UvicornWorker`.
- **DigitalOcean App Platform:** `.do/app.yaml` defines a `backend` service (Dockerfile; routes `/api`, `/_allauth`, `/admin`, `/static`; `RUN_MIGRATIONS=false`), a `frontend` `static_site` (Vite build, `catchall_document: index.html` for SPA routing, `VITE_*` as `BUILD_TIME` env), a managed `db` (Postgres), and a `PRE_DEPLOY` `migrate` job (so web replicas never race migrations). `${db.DATABASE_URL}` and `${APP_DOMAIN}` are App Platform bindable vars; `SECRET_KEY`/`EMAIL_*` are `type: SECRET`. Validate with `doctl apps spec validate .do/app.yaml` (needs `doctl auth init`).
- **PMTiles hosting:** production tiles live in **DO Spaces**. The Spaces bucket CORS must allow the frontend origin with `GET`/`HEAD` + the `Range` header and expose `Content-Range`/`Accept-Ranges`, or the browser blocks the range requests and the basemap is blank.

## Conventions

- Hosts/URLs are env-driven, not hardcoded: backend via `FRONTEND_URL`/`ALLOWED_HOSTS`/`DATABASE_URL`, frontend via `VITE_API_URL`/`VITE_*`. Keep both sides in sync when changing origins.
- New geospatial features generally mean: model field in `api/models.py` → migration → schema in `api/schemas.py` → tagged endpoint in `api/api.py` → consume from a store/component in the chosen client.
- Per user instruction, the web client stays plain JavaScript (no TypeScript).
